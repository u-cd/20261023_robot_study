# ACT実機検証の到達点 — 2026年11月7日

記録日：**2026-11-07（日本時間）**。この日の終了時点の結果を残すためのまとめ。

対象は、①初期検出値入力の小型ACT、②画像入力のフルサイズACTの2モデル。②をRunPod GPUとローカルCPUで動かしたものは、同じ重みを使う同一モデルであり、別の学習モデルとして数えない。

## 1. 今日の到達点

**RunPodで学習した画像入力ACTを、このPCのCPUへ移して推論し、スポンジをつかんでcoin付近へ運び、手動の位置調整後に解放・退避まで進む一連の動作を確認できた。**

画像入力ACTのローカル推論は約0.5〜0.6秒。20制御ステップに1回の推論なら、ユーザーの評価ではリアルタイムに近い、十分実用的な速度で動作した。今後の検証を、RunPodを常時起動せずにこのPCで続けられる状態になった。

一方、**coin付近から解放へ進めずに動作がループする問題が残る**。手動で位置を微調整すると、その後は自動で最後まで進む挙動がRunPod・ローカルCPUの両方で見られた。完全無介入で安定して成功する段階には、まだ到達していない。

## 2. 共通のタスク・データ・学習条件

### 実機とタスク

- Adeept ADA031 V4.0、Arduino UNO互換基板、固定Webカメラ1台。
- スポンジをつかみ、coin付近へ運び、coinの上へ離してアームを退避させる。
- 関節順は台座・肩・肘・手首・グリッパーの5次元。
- 開始姿勢は **70°・113°・43°・80°・90°**。
- 基板から取得しているのは指令角度。関節の実角度・接触・把持成否を直接測るセンサー値ではない。

### 実演データ

ユーザー自身が操作した成功実演50回を使用。アームの開始姿勢、カメラとアームの設置を固定し、スポンジとcoinの位置を実演ごとに変えて収集した。

|項目|内容|
|---|---|
|実演数|50回|
|学習・検証|実演単位でtrain40 / validation10。両モデルで同じ分割|
|画像|RGB 640×480、topカメラ1台|
|学習用の周期|20Hz、1ステップ50ms|
|全ステップ数|46,694|
|実演ごとの長さ|599〜1,287ステップの可変長|
|長さの加工|全実演を同じ長さへ時間伸縮せず、停止区間も自動削除していない|
|学習時の末尾処理|未来100ステップに足りない部分をpaddingし、is_padで損失から除外|
|入出力の単位|5関節ともラジアン。基板への送信境界で整数の度数へ変換|
|action対応|整列済みデータのaction_offset=0|

元の生記録は `data/act_demonstrations_raw/`、HDF5は `data/act_training/demonstrations_50_20hz/`。元データは保持し、派生データで上書きしていない。

### 学習条件

両モデルともbatch8、seed0、5,000 epoch。1epochは各学習実演から開始時刻を一様抽出する40サンプルで、5回のパラメータ更新を行う。全フレームを毎epoch走査する意味ではない。合計25,000更新。

AdamW、lr1e-5、weight decay1e-4、masked L1＋KL重み10を使用。公式に合わせて全50実演から平均・標本標準偏差を計算し、std下限を0.01とした。検証損失で最良重みを選択しているため、validationは独立した最終テストではない。

## 3. モデル①：初期検出値入力の小型ACT

### 構成

YOLOv8nで開始前の異なる5フレームからspongeとcoinを検出する。各クラスの最大信頼度bboxの中央値を取り、実演・試験中はその初期検出値を固定する。検出器の手動正解ラベルは監査用であり、ACTに渡す検出値を正解で置き換えていない。

各物体の入力は `[cx/W, cy/H, width/W, height/H, confidence, valid]` の6特徴。sponge・coinの2トークンと現在の5関節指令角度を使い、画像バックボーンを外したACTへ入力する。

|項目|設定|
|---|---|
|hidden / heads / FFN|192 / 3 / 768|
|Transformer encoder / decoder|4層 / 7層|
|CVAE encoder / 潜在次元|4層 / 32|
|chunk|100ステップ×5関節|
|パラメータ数|7,758,406|
|推論時のz|0|
|学習・推論の計算精度|float32|

学習は完了し、最良validation lossは0.074882、epoch 4455で得た。実行全体は約17,549秒、約4時間52分。

### オフライン評価

最良重みを使い、検証10実演の各64開始時刻で、記録された現在の指令角度を入力して評価した。実機を自由に動かした評価ではない。

|関節|予測chunk全体のMAE（度）|現在角度を維持する予測のMAE（度）|先頭1ステップのMAE（度）|
|---|---:|---:|---:|
|台座|3.612|3.426|1.420|
|肩|3.881|4.498|1.639|
|肘|3.284|3.091|1.238|
|手首|0.001|0.000|0.001|
|グリッパー|6.226|5.565|1.782|

先頭の誤差は小さくても、未来chunk全体では角度維持の基準予測を多くの関節で上回れていない。これは実機でうまく動くと結論する十分な結果ではない。手首は実演でほぼ固定されており、その小さい誤差を難しい動作を学べた証拠とは扱わない。

モデル推論の中央値27.23ms、p95 30.39ms。検出器・カメラ・基板通信の時間は含まない。

### 実機の結果と留保

ユーザー報告では、何回か動いた後に動かなくなり、スポンジの把持には至らなかった。検出モデル自体は問題ないという確認だった。

ただし、この時の試験UIは、毎回予測したchunkの先頭1ステップだけを使用し、1更新の変更量を2°以内へ制限し、手首の出力を80°に固定していた。後の画像入力ACTのtemporal aggregationありの試験とは実行条件が異なる。**失敗原因を、検出値入力やモデルの小型化だけに断定できない。**

当面、このモデルの原因調査は保留し、画像入力ACTの検証を優先する。

## 4. モデル②：画像入力のフルサイズACT

### 構成と学習

公式ACTの画像入力モデルを土台にし、5関節へ対応させた。入力は現在の画像と関節指令角度で、検出器は使わない。

|項目|設定|
|---|---|
|バックボーン|ImageNet事前学習のResNet18|
|hidden / heads / FFN|512 / 8 / 3200|
|Transformer encoder / decoder|4層 / 7層|
|CVAE encoder / 潜在次元|4層 / 32|
|chunk|100ステップ×5関節|
|パラメータ数|約8,390万|
|学習場所|RunPod A40|
|推論時のz|0|

学習ループは約3時間59分。最良validation lossは0.065415、epoch 3438で得た。学習完了後の重み・正規化統計は永続ストレージへ保存され、最良重みはこのPCにも回収した。

最良重みのSHA-256：

```text
6298b246a7a2f55c518427764d91f94ec32dcccb48a7ed2b9e3e72f6710d7fe6
```

### 実機試験で使った推論手順

最初の基準条件は、現在画像・現在角度から毎更新で推論し、公式のtemporal aggregation（k=0.01）を使う方式。公式のゼロ行除外、古い予測からの行順、重み付け・正規化を維持し、集約後にactionを逆正規化する。

公式の集約計算を共用関数として切り出し、元の処理との一致をテストした。外部コードの変更は `patches/act_cpu.patch` に保存し、理由・元コミット・適用方法を記録している。

画像入力版では、小型モデルの初期UIにあった独自の2°クリップと手首出力の固定を外した。基板へは絶対目標角度を整数度へ丸めて送信する。基板速度は実演時と同じ25°/秒。指令範囲外の予測は自動で置換せず停止する。

これはモデル・集約処理を公式に合わせた実機アダプターであり、公式ALOHAの実測14関節・50Hz環境そのものではない。

### RunPod推論からローカル推論への移行

クラウド推論では、GPU forward自体よりも、画像の送受信を含む待ち時間が大きかった。このため、同じ最良重み・正規化統計をローカルCPUへ移し、モデルを小型化せずに推論できるかを検証した。

|測定|結果|範囲・条件|
|---|---|---|
|RunPod上の完了時オフライン確認|平均11.20ms|最終重みpolicy_last、同じ記録観測で5回。実機通信なし。最良重みの実機試験とは別条件|
|GPU推論サービスのforward|約54ms|最良重み、クラウド通信試験内の3回|
|クラウドへの画像送信から応答|3,166 / 1,619 / 1,355ms|約777KBのPNG入りJSON、重み転送終了後の3回。少数測定|
|ローカルCPUのforward中央値|531.29ms|最良重み、ウォームアップ3回後12回|
|同forwardのp95|676.31ms|同上|
|画像前処理込みのローカル中央値|533.43ms|カメラ取得・集約・基板通信は除く|
|ローカルプロセスの最大RSS|約955MiB|モデル構築中を含む高水位|

ローカルCPUの測定条件はi7-8550U、PyTorch2.5.1+cpu、float32、演算2threads・interop1thread。同じ保存済み640×480カメラ画像・開始角度で計測した。

GPU・CPUの数字は計測方法・重み・稼働条件が一部異なるため、単純なハードウェア速度比とはしない。ローカル入力処理と公式 `get_image` 経路の予測の差も確認し、正規化出力の最大差約6.56e-7で許容誤差内だった。GPUとの同時数値比較は、当該確認時にトンネルが利用できず実施できていない。

### 推論頻度の間引き

ユーザー指定で、毎回推論に加えて **20制御ステップに1回の推論** を試した。これは20Hzの学習データで「元の1秒分」に相当する。間の19ステップでも指令を送り、予測chunkの該当する要素を使って有効な予測を集約する。

制御ステップ0・20・40…で推論する方式であり、実時間で必ず1秒ごとに推論する意味ではない。同期的な推論待ちと基板通信があるため、20ステップの実時間は1秒を超える。temporal aggregationは維持するが、推論頻度を変更した実験として毎ステップ推論の基準と区別する。

ユーザーのローカル実機評価では、平均の推論時間は約0.5〜0.6秒で、20回に1回ならリアルタイムに近い速度で十分動作した。**これは体感を含む実用上の評価であり、全体が厳密な20Hzで動いたという測定結果ではない。**

### 実機でできたこと

1. RunPod推論で、台座の手動微調整1回を挟み、それ以外はモデルで搬送の一連の流れを完了できた。ユーザー評価は「概ね成功のライン」。
2. 再試行でもcoin付近でループしたが、手動の位置調整後は残りのグリップ動作・解放まで自動で進んだ。
3. 同じ重みを使ったローカルCPUでも問題なく実行できた。coin付近でループし、手動調整後に最後まで進む挙動までRunPod推論時と一致したというユーザー報告だった。

これらを **「手動介入を伴うタスク完遂」** として記録する。全試行の正確な総数・配置条件・介入数の集計は行っていないため、成功率や完全自律での再現性の数値は出さない。

## 5. 残っている中心的な問題：coin付近のループ

スポンジをcoin付近まで運んだ後、解放へ進まず、近い姿勢を繰り返すことがある。手動の位置調整によって先へ進む。これが現時点でユーザーが認識している主な問題である。

確認した試験ログの一例では、末尾20更新で台座90〜91°、肩111〜112°、肘31〜32°、グリッパー145〜146°付近の目標が繰り返し送られていた。新しい指令が全く送られていないだけの状況とは異なる。

### 本人の仮説

実演中、coin上へ正しくスポンジを落とすために微調整が必要だった。そのデータが、モデルにとって「coin付近の姿勢で微調整を繰り返す」挙動として学ばれ、解放へ進まなくなる可能性がある。

これは未検証の仮説。手動調整で画像・関節角度・実物の位置が変わるため、調整後に進んだことだけでは、原因を実演中の微調整に確定できない。間引き、過去予測の集約、入力の曖昧さ、実機誤差なども未分離である。

同じ問題がローカルでも再現したことで、クラウド通信だけを原因とする説明は支持されにくくなった。ただし、通信遅延以外の実行時の時間差の影響まで否定したものではない。

## 6. 終了条件の現状

公式ACTの評価コードは、設定されたepisode_lenの更新回数を実行して終了する。タスク完了をACTが判断して停止する仕組みではない。現在の実機試験にも、自動の成功判定・終了判定は入れていない。

画面は1回・10回・連続最大1000回の更新を指定でき、指定回数または30分で停止する。人の停止要求、通信異常、指令範囲外でも停止する。タスク完了後に推論を続けても、終了姿勢を維持する保証はなく、再び動く可能性があるため、完了を確認したら人が「停止・保持」を押す。

## 7. 次回の検証につながる結論

今日の成果は、画像入力ACTの学習から実機での搬送、さらに同じモデルのローカルCPU運用までつながったこと。高速な小型モデルの試験は搬送に至らず、速度だけでは実機の成立性を判断できないことも確認対象として残った。

今後の計画の正本は[ルートの実験計画とメモ](../experiment_plan_ja.md)。本書は今日の結果のスナップショットとして残す。次回の優先課題は、coin付近で手動介入する直前・直後の画像、角度、集約前後の予測を比較し、ループの原因を絞ること。その後、推論間隔の比較と終了条件の検討を進める。

モデル重み・生記録・試験ログは残す。今後リポジトリを整理するときも、この到達点を再確認できる資料と必要なモデルの所在を保持する。
