# 次回候補：模倣学習でスポンジを運ぶ

記録日：2026年10月31日。当初の検討案を含む文書。現在は成功27試行でのBC学習、台座補助、関節グループの順番固定まで実装・試行した。**次回は[工程設計とデータ作り直しのメモ](next_session_motion_data_plan_ja.md)を優先する。**

## データの保存方針（更新）

ユーザーの希望により、成功例だけを残す。失敗・中断では画像と操作記録を試行フォルダごと削除する。以下の失敗・回復動作の活用は将来の検討事項であり、現行の収集では失敗例を蓄積しない。

## 段階の更新

ユーザーの実操作に合わせて「つかむまで」「はなすまで」「退避」の3段階に統合した。スポンジをつかめたら2、グリップを開いてスポンジを離し終えたら3へ切り替える。入力は検出特徴8＋関節指令4＋段階3の15項目。各段階内の微調整・操作順は自由。

## 今のプロジェクトでの判断

**次回、模倣学習の小さな実験から始めることは有力な選択肢。幾何モデルの精密化や紙面校正の追加を先に完了する必要はない。**

スポンジをつかんで持ち上げ、ターゲットへ運ぶことは実機で成功している。人が成功動作を示せるので、その操作を教師データとして集められる段階に来た。カメラとアームが固定され、机・スポンジ・把持高さを揃える条件なら、画像上の位置から関節指令を学び、実行時のホモグラフィーや逆運動学計算を省く構成を試せる。

ただし、**模倣学習なら必ず早い・簡単という結論にはまだならない。** 幾何の式を作る作業が、成功例の収集・時刻の対応づけ・失敗時のデータ追加へ置き換わる。現在のCPU環境では、画像から動作全体を学ぶ大きなモデルより、既存の検出結果を使う小さなモデルから試す方が開発・検証の負担を抑えられると考える。これは本プロジェクトについての提案であり、実測済みの学習時間・成功率ではない。

## 比較する3つの構成

| 構成 | 入力 → 出力 | 学習する範囲 | このプロジェクトでの位置づけ |
| --- | --- | --- | --- |
| 段階別の姿勢回帰 | 物体のピクセル位置＋段階 → 関節指令 | つかめる姿勢・置ける姿勢など | 少量の対応点で最初に比較しやすい。順序と速度はプログラムが担当 |
| 検出特徴を使うBehavior Cloning（BC） | 検出結果＋現在の指令＋必要なら履歴・段階 → 次の操作 | 人の操作の選び方 | 次回の模倣学習の小規模試行として推奨する候補 |
| 画像を使う時系列の模倣学習（ACTなど） | カメラ画像＋状態・履歴 → 動作列 | 視覚特徴と動作列 | 将来候補。同期した連続記録、機体への接続、計算負荷の確認が増える |

BCは、人の観測と操作の組から操作を予測する方策を教師ありで学ぶ方法。単に保存角度を同じ順で再生するだけでは、新しい物体位置に応じた操作を学んだことにはならない。

ACTは画像と関節状態から一定区間の動作列を予測する模倣学習の手法。LeRobotは同期した画像・状態・操作のデータ形式と方策実装を提供する。ただし、このAdeept機と現在の通信方式がそのまま使えるとは限らず、接続部分の実装・依存関係の適合確認が必要。[ACT原論文](https://arxiv.org/abs/2304.13705)、[LeRobot公式](https://huggingface.co/docs/lerobot/index)。

## 最短の試行案

1. 既存の操作UIに「デモ記録開始・成功で終了・失敗で終了」を追加する。実機を動かしながら撮影時刻と指令の時刻を連続記録する。
2. 固定カメラ・同じスポンジ・手首固定で、無理なく届く複数の配置を人が操作して運ぶ。まず5〜10試行程度で記録の欠落・同期・再生確認を行う。この件数で学習精度が十分という意味ではない。
3. 既存YOLOのスポンジ・ターゲットの位置、信頼度、検出有無と、関節指令を入力にした小さなMLPを試す。CPUでの学習・推論時間を測る。
4. 最初の出力候補は「どの関節を増やす／減らす／待つか」。実機で希望している1関節ずつの操作と合わせやすい。段階を入力する場合、その切り替えは既存の処理が担当し、段階判断までAIが学んだとは扱わない。
5. 未使用の配置で短い区間から動かし、把持・持ち上げ・搬送・解放の成否を記録する。姿勢回帰の単純な基準と比較し、どちらが少ない手間で成功するかを見る。

最初からACT・Diffusion Policy・大きなVLAの導入を前提にしない。小さいモデルの結果や検出の遮蔽が限界なら、画像入力・短い履歴・ACTなどを検討する。LeRobotを採用する場合も、まず互換性を確認し、現在のuv環境を無条件にアップグレードしない。

## 記録するもの

| 記録 | 内容・理由 |
| --- | --- |
| エピソードID | 1回の把持から搬送終了までを区別する |
| カメラ画像・撮影時刻 | 後から特徴の再抽出や動作確認に使う |
| 検出結果 | スポンジ・ターゲットの枠、中心、信頼度、検出有無、元フレームID |
| 指令前の状態 | 直前に確認できた各関節の指令値、保持状態、速度設定 |
| 人が送った操作 | 関節、方向、目標指令、送信時刻、応答時刻、受理されたか |
| 実行間隔 | 実際のdt、画像と指令の時差、フレーム欠落を記録する |
| 段階と結果 | 接近・把持・上昇・搬送・解放、成功／失敗、失敗理由、修正操作 |
| 条件 | カメラ配置、机、物体、手首、把持・解放高さ、グリップ角度 |

**入力画像・状態は操作を決める前、教師ラベルはその後に出した操作として対応させる。** 操作後の画像を操作前の入力として扱うと、実行時には得られない情報を使う学習になる。複数操作が非同期に重なった場合も、時刻とフレームIDから追える形にする。

この機体は実際の関節角度を返さない。`STATUS` は指令値であり、負荷で動けなくても数字だけ変わる場合がある。記録には「実角度ではない」と明記する。電源を切って手でアームを動かしても、その姿勢を現在の仕組みで読み取ることはできないので、最初の教師データは操作UIで動かして集める。

操作待ち・物理的な移動待ち・把持待ちを記録し、何も操作していない区間をすべて同じ理由とみなさない。今のぎこちなさをそのまま学ぶ可能性があるため、動作速度と通信待ちの改善は模倣学習とは別に必要。記録速度だけを変えてもサーボの応答が速くなるわけではない。

## 既存データをどう使うか

- **60枚の検出用画像**：物体の検出学習には使えるが、人の連続操作ラベルがないので、そのまま搬送方策のデータにはならない。
- **11点の関節指令・写真**：位置と姿勢の対応を調べる初期資料として使える。把持・上昇・解放までの連続デモではない。
- **今回の成功試行の段階写真と指令**：成功姿勢・条件・開始点の参考になる。連続記録を後から完全に復元できるとは扱わない。
- **紙面校正**：残して、実機誤差や到達範囲をmmで比較する基準にする。画像から操作を学ぶ方策の必須入力にはしない。

## 比較・評価の決め方

- 学習と評価はエピソード・物体配置ごとに分ける。同じ動画の隣接フレームをランダムに両方へ混ぜない。
- 最初は位置以外の条件を固定し、学習配置と未使用配置での把持成功率・搬送成功率・介入回数・所要時間を分けて記録する。
- 指令の予測誤差だけでは成功を判断しない。アームに隠れて検出が消えること、把持し損ねること、指令に機体が追従しないことも観察する。
- データの外の位置、古い画像、検出欠落でそのまま操作を継続しない。可動域と1回の変化量は既存の制御側で制限する。
- 失敗からの修正を教師データに追加する場合、失敗動作と人の回復操作を区別する。成功例だけでは学習時に見なかった状態へずれたときに戻れない可能性がある。

## 次回の最初の判断

次回は「幾何校正をさらに詰める」ことを既定路線にせず、**成功動作の記録機能を作り、特徴ベースの小さな模倣学習を試す**案を最初に検討する。把持・解放の入力高さ5mm、下降時は台座→肘→肩／上昇時は逆順、速度・グリップ角度の改善希望を記録設計に引き継ぐ。

記録機能を揃えれば、同じデータから「段階別の姿勢回帰」と「次の操作を学ぶBC」の両方を比較できる。どちらが早く簡単かは、データを集めた実際の手間と未使用配置での成功率を見て決める。
